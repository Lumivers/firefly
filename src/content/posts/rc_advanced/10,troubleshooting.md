> 赛场上车出了故障，最怕的不是 Bug 本身，而是在备赛区不知道到底是哪里的问题——上位机说是电控没发回包，电控说是机械卡死，机械说是上位机发的指令不对。三方互相争论半小时，宝贵的调试时间全浪费了。这一章总结赛场上最高频的故障症状、排查技巧，以及如何利用框架提供的审计工具快速定位问题。

# 常见症状与根因映射

车在赛场上出现异常走位或动作停滞时，不要凭空猜测，先对着现象排查：

### 1. 蛇形走位（直线画龙）
* **现象**：小车走直线时车头一直左右小幅摆动，甚至越摆幅度越大。
* **原因 A（定位高频噪声）**：里程计或测程轮有微小机械跳动，Pure Pursuit 每一帧都在过度修正噪声。
  * **验证**：查看定位输出，如果坐标轨迹呈高频锯齿状，调大第 5 章讲的低通滤波，或者在第七章中拉大前瞻距离 \(L_d\)。
* **原因 B（控制增益过大）**：如果定位轨迹很平滑但车身剧烈抖动，说明角速度转向增益 \(P\) 给太高，发生超调震荡，适当降低转向灵敏度。

### 2. 过弯过冲（转不过弯、冲出赛道）
* **现象**：到了弯道该转向时车头反应迟钝，整台车切大弯甚至冲出场地。
* **原因（通信与解算延时过大）**：拿到全局坐标时已经是 80~100ms 之前的数据，Pure Pursuit 用过去的位姿计算当前的控制量，速度越快过冲越严重。
  * **验证**：检查串口通信频率（确保下位机上报达到 50Hz~100Hz），检查上位机是否有耗时繁重的任务（如图像处理未开独立线程）卡住了主循环。

### 3. 坐标瞬变与 90° 甩尾（血泪教训）
* **现象**：车走得好好的，突然猛打方向甚至直接 90 度原地甩尾。
* **原因 A（雷达过热漂移，真实踩坑）**：
  > **这里特别提醒一个很多人容易忽视的硬件隐患**：雷达和计算板的散热。  
  > 比如我们 26 赛季用的 Odin1 激光雷达，在封闭车壳内由于没有做针对性散热，比赛跑了几轮后**雷达因为芯片过热出现了严重的原点漂移**，导致比赛途中发生重大事故。传感器在高温环境下的硬件特性会剧烈恶化，装车时必须给高发热传感器留好通风风道或小风扇。
* **原因 B（打点校正跳变）**：工位激光测距打在立柱边缘出现打空跳变，上位机把错误读数当成了绝对基准，直接修正了当前位姿。必须像第 5 章那样加上量程过滤与中值滤波。

### 4. 原地发呆卡死（状态机不往前走）
* **现象**：底盘到点了，机械臂没有任何动作，或者机械爪夹完后车就不动了。
* **原因**：典型的事件丢失或回包等待超时（详见下一节的黑匣子排查）。

# 利用 `robocon-fsm` 超时黑匣子快速破案

在以往的开发中，调试异步代码最让人头疼的是控制台抛出一个孤零零的 `TimeoutError`，你根本不知道是在等谁超时、到底谁没发信号。

在 `robocon-fsm` 框架中，所有事件在总线上都有轻量审计记录。一旦某个动作超时，系统抛出的 `FSMTimeoutError` 会自动附带**总线历史黑匣子**：

```
FSMTimeoutError: 等待事件 'GRIPPER_DONE' 超时 (3.0s)。
最近总线事件记录: ['NAV_DONE', 'DT35_ALIGNED', 'HEARTBEAT']
```

看到这条诊断日志，你 1 秒钟就能把责任划分清楚：
1. `NAV_DONE` 到了：说明底盘导航正常完成；
2. `DT35_ALIGNED` 到了：说明激光打点校正也跑完了；
3. `HEARTBEAT` 持续刷新：说明串口通信链路完全通畅；
4. **唯独没有 `GRIPPER_DONE`**：直接定位问题——电控没有发爪子到位的确认包，或者气缸根本没压到微动开关。

不用开调试器，直接对着终端日志找电控同学看这一处即可。

# 抓包验证与高效定责法

在赛场备赛区，为了防止三方互相推诿，最快的办法是用数据说话。

通过 ROS 2 命令行工具逐层验证数据流：

```
决策层 (my_decision) ──► 动作接口 (my_actions) ──► 串口驱动 (robot_serial) ──► 下位机单片机
```

### 1. 查动作指令有没有发出来
如果机械爪没动，先看上位机有没有下发指令：
```bash
ros2 topic echo /robot/gripper_cmd
```
* 如果有数据刷新，且 `cmd` 字段符合协议：说明上位机决策逻辑完全正常，问题在串口驱动或者电控单片机上；
* 如果压根没有数据：说明上位机代码压根没执行到这一步（卡在上一步等待了）。

### 2. 查底盘控制速度有没有输出
如果小车原地不动：
```bash
ros2 topic echo /cmd_vel
```
* 如果速度全为 0：检查状态机是否已经给底盘发了停车，或者路径点已到达；
* 如果速度非 0 但底盘不走：检查串口线连接、下位机驱动使能开关或急停按键。

### 3. 利用 rosbag 记录赛场黑匣子
每场比赛试车前，在启动脚本里加一行录包命令：
```bash
ros2 bag record -o match_test /odom /cmd_vel /robot/gripper_cmd /robot/gripper_status
```
跑完无论成功还是失败，把数据包存下来。回到工位用 `ros2 bag play` 回放，对齐时间戳逐帧看，故障原因一清二楚，不用靠记忆复盘。

# 团队技术资产沉淀：给下一届留什么？

赛季结束后，代码往往会随赛题变化而更替，但**工程架构和踩坑经验**是战队最宝贵的技术资产。

不要只留一堆写满个人随手注释的零碎脚本给学弟学妹。一份合格的上位机交接仓库应当做到：

### 1. 统一的项目结构（以模板化为主）
直接把验证成熟的工程整理成开箱即用的模板目录（如 `templates/standard_robot/`）：
```
standard_robot/
├── config/params.yaml    # 所有工位坐标与调优参数
├── my_actions.py         # 封装好的整车硬件动作接口
├── my_decision.py        # 纯粹的线性战术业务逻辑
├── main_node.py          # 包含参数加载与一键重置的入口节点
└── README.md             # 快速上手指南
```

### 2. 清晰的交接说明（30 分钟跑起来）
交接文档里不需要长篇大论讲数学推导，必须讲清楚三件事：
1. **环境怎么装**：系统版本（Ubuntu 22.04）、依赖包安装命令；
2. **脱机仿真怎么跑**：没有车的时候，怎么运行第八章的 Mock 决策仿真看全场逻辑；
3. **通信协议怎么对**：结构体各字段含义、CRC16 校验方式、帧头定义。

新队员拿到仓库，按照说明在个人电脑上 30 分钟内把虚拟仿真跑通，能够看懂全场代码是怎么一行行执行的，这套系统的传承才算真正做扎实了。

# 小结

1. **查故障看数据不靠猜**：遇到蛇形走位查滤波与前瞻距离，遇到过弯过冲查通信延迟，遇到坐标瞬移查传感器噪点与散热。
2. **硬件散热不可忽视**：激光雷达和工业相机发热严重，必须做好物理散热，防止芯片过热导致原点偏移和跳点。
3. **利用总线黑匣子自证清白**：通过 `FSMTimeoutError` 的历史事件日志，秒级确认停滞原因，拒绝低效甩锅。
4. **留模板不留死代码**：把经过实战检验的架构封装成标准模板留给下一届，让新队员在开箱即用的脚手架上起步。
