> 这一章讲的是我在做比赛过程中重构最彻底的一部分：把早期写得头疼的多层嵌套 C++ 状态机，改成用 Python `asyncio` 协程来驱动。改完之后，赛前改比赛路线和作业顺序就变得非常直观了。

# 为什么决策层选 Python 而不是 C++？

在工科竞赛里，很多同学可能会觉得“机器人系统全栈都得用 C++，Python 性能不够”。

但在实际分工中，决策层和控制层做的事情完全不同：

1. **决策层不需要密集的数值计算**  
   决策层干的事情基本是：“开到取物区 $\to$ 抓取物块 $\to$ 开到发射区 $\to$ 发射”。每个动作之间间隔几百毫秒甚至几秒，根本没有高频复杂的矩阵运算。真正吃 CPU 算力的是串口通信、底盘运动学解算和视觉检测，那些跑在独立的底层节点里。决策层本身消耗的算力其实极低。
2. **Python 的异步语法改战术更快**  
   如果用 C++ 写异步状态机，往往要写大量的枚举、switch-case、回调函数，或者折腾 C++20 相对复杂的协程模板。一旦比赛现场临时需要修改取物路线，改动一个状态可能要牵扯好几个文件。  
   而 Python 的 `async/await` 写起来和普通的顺序流程几乎一样，比赛现场如果需要换路线，改几行代码保存就能跑，现场改战术的容错率高很多。

> **分工建议**：  
> 算力密集、对时序敏感的底层（串口协议、底盘运动控制、图像采集）用 C++；上层业务逻辑（决策调度、全场走位路线）用 Python。两者通过 ROS 2 话题或者内部 IPC 通信解耦，各司其职。

# 阻塞式代码的问题

先看一段很多新手在写动作等待时容易写的代码：

```python
# 常见但有隐患的写法：阻塞式等待
def grab_block(block_id):
    send_arm_command(block_id)     # 1. 往下位机发抓取指令
    while not arm_done_flag:       # 2. 循环等电控回包
        time.sleep(0.1)            # 每 100ms 查一次标志位
    send_next_action()             # 3. 机械臂完成了，继续下一步
```

这段逻辑表面上看很直接：发指令 $\to$ 等完成 $\to$ 下一步。

但 `time.sleep` 是一个**同步阻塞**调用。在它休眠的这段时间里，当前线程被完全挂死：
- 裁判吹哨或者操作手按手柄急停，程序无法及时响应；
- 底盘里程计的回调被堵在队列里无法更新；
- 传感器和串口数据如果积压在缓冲区，可能导致后续处理出现延迟。

万一机械臂在场上发生机械卡壳，标志位一直不变，程序就会一直死循环在这个函数里，整台车在原地动弹不得。

# 协程的解法：发指令后挂起，由事件唤醒

协程的思路是：**发完指令后立即挂起当前函数，把线程控制权交还给事件循环；等目标事件到达时，再由事件循环恢复执行。**

```python
async def grab_block(fsm, act, block_id):
    act.send_arm_command(block_id)             # 1. 发送硬件指令
    event = await fsm.wait_event("ARM_DONE")   # 2. 挂起！把执行权让出去
    # 收到电控的 ARM_DONE 事件后，自动从这里继续往下走
    act.send_next_action()
```

两者的本质区别：
- **`time.sleep`**：线程死等，任何外部消息、急停和回调都处理不了；
- **`await` 挂起**：当前任务让出 CPU，事件循环继续高速处理心跳、急停和传感器数据，等事件来了再无缝切回来。

# 赛场现实：电控没写回调怎么办？被迫的“异步盲等”

上面讲的“发指令 $\to$ 等事件”，前提是**下位机动作做完后会主动给上位机发确认回包**。

但在真实的备赛和比赛现场，经常会遇到一种无可奈何的情况：
1. **机械上根本没装传感器**：比如气缸开闭、舵机下潜、无编码器的推杆。电控在物理硬件上根本不知道动作什么时候做完；
2. **电控进度紧张没写回包**：备赛时间不够，电控只写了接收指令的代码，压根没做状态机和完成确认帧。

上位机发了指令过去，下位机就像黑洞一样没有任何回复。这时候如果不等，下一步动作就抢跑了；如果去 `wait_event`，就会直接死等超时。

**即使不想写 sleep，现实中也往往不得不写。**

但即使迫不得已要盲等，**写法上也有本质区别**：

### 1. 绝对不能写 `time.sleep`
```python
# 迫不得已，但写了同步 sleep（严重隐患）
act.send_pneumatic_open()
time.sleep(0.5)  # 致命：这 500ms 内整车线程卡死，按急停都停不下来！
```

### 2. 正确的妥协做法：使用异步延时 `await asyncio.sleep`
```python
# 迫不得已的盲等，但使用协程异步挂起
act.send_pneumatic_open()
await fsm.wait(0.5)  # 或者 await asyncio.sleep(0.5)
# 这 500ms 里虽然也是估算延时，但控制权交还给了事件循环，急停和底盘保活依然正常运转
```

### 3. 工程上的建议：封装与参数化

不要把盲等硬编码在决策业务代码里。应该在底层的动作接口里把它封装好，并且把延时时间抽离成配置文件（YAML）里的参数：

```python
# actions/arm_actions.py
async def open_gripper(act, fsm, wait_time=0.5):
    """
    由于爪子是气缸驱动没有到位开关，发指令后盲等设定时间
    """
    act.send_gripper_command(cmd=1)
    # 使用异步等待，保证急停和主循环不卡死
    await fsm.wait(wait_time)
```

在参数文件 `config.yaml` 中配置：
```yaml
gripper:
  open_blind_wait_sec: 0.5  # 气压足时 0.5s，气压不足现场改 0.7s
```

这样就算现场气泵压力不稳定导致气缸变慢，你只需要在配置文件里改一下时间，不用去动代码逻辑。

# 时序防坑：先挂号，后发指令

在设计“发指令 $\to$ 等回包”的逻辑时，很容易踩进一个偶发性的时序竞态问题。

### 容易踩坑的写法：“先发指令，后等待”

```python
async def bad_action(fsm, act):
    act.send_hardware_command()           # ① 先发串口指令
    # ── 如果下位机回包极快，就在这里插入 ──
    await fsm.wait_event("ACTION_DONE")   # ② 再挂起等待事件
```

在本地仿真或者下位机回包较慢时，这段代码通常看起来正常。

但在真实车上，如果下位机响应极快（比如单片机在几十微秒内直接回包），或者进程内部通信：
1. ① 指令刚发出去；
2. 下位机瞬间回包，串口接收线程立马收到并触发了 `post_event("ACTION_DONE")`；
3. 但此时 ② 的 `wait_event` 还没来得及向状态机注册这个等待项；
4. 状态机发现当前没人等这个事件，就把它当成旧事件忽略了；
5. 接着 ② 开始执行并挂起等待，但那个确认信号已经错过了；
6. 结果就是：动作明明做完了，程序却一直卡在等待里，直到超时。

这种 bug 往往表现为“偶尔卡死一次，加了个 print 打印之后又好了”（因为 print 消耗的时间改变了时序）。

### 可靠的解法：先挂号，后发指令

规范的等待时序应当是：**先在状态机里把等待项注册好，再去发送物理指令。**

```python
async def safe_action(fsm, act):
    # 1. 先挂号：在状态机内部预先生成一个 Future
    fut = fsm.create_waiter("ACTION_DONE")
    try:
        # 2. 后发指令：此时哪怕下位机立即回包，Future 也能准确捕获
        act.send_hardware_command()
        # 3. 挂起等待刚才挂好号的 Future
        event = await fsm.wait_future("ACTION_DONE", fut, timeout=3.0)
        return event
    finally:
        # 确保异常退出时清理等待者，防止残留
        fsm.cancel_waiter(fut)
```

这样无论下位机通信有多快，确认信号都不会漏掉。

# 常用调度模式与超时诊断

在实际比赛中，除了单个动作等待，还有几种常见的异步调度模式：

### 1. 边走边做动作（并行等待）

在赛场上为了节约时间，通常需要小车在开往目标区的路上，机械臂就提前抬起到位：

```python
# 导航的同时提升机械臂，两者都完成才进入下一步
await fsm.wait_all(
    act.navigate(bb.target_x, bb.target_y),
    fsm.wait_event("ARM_LIFT_DONE"),
    timeout=6.0
)
```

### 2. 竞争等待（谁先触发就处理谁）

例如在导航过程中，同时监听避障传感器：

```python
# 边走边检测障碍物：如果正常到点则继续；如果半路被挡住则切换策略
winner = await fsm.wait_any("NAV_DONE", "OBSTACLE_BLOCKED", timeout=5.0)
if winner.type == "OBSTACLE_BLOCKED":
    act.get_logger().warn("行进受阻，切换备选路线")
    await fallback_route(fsm, act, bb)
```

### 3. 超时诊断信息

调试赛车时，最怕控制台只弹出一句冷冰冰的 `TimeoutError`，看不出这几秒里到底发生了什么。

在状态机设计中，可以在超时异常里附带最近收到的事件列表：

```
TimeoutError: 等待事件 'GRIPPER_DONE' 超时 (3.0s)。
最近总线事件记录: ['NAV_DONE', 'DT35_ALIGNED', 'HEARTBEAT']
```

看到这条日志，就能快速确认：底盘到点了，激光也对准了，心跳也是正常的，唯独没有爪子的回包。排查方向立刻就明确了——要么是电控没发包，要么是微动开关没压到位。

# 动作与战术逻辑解耦

采用协程后，工程结构建议分成清晰的两层：

* **原子动作层（`actions.py`）**：
  专门负责单个机构动作的具体执行，包含发指令、等回包、超时重试，以及前面提到的无回包盲等。这一层与具体硬件相关，机械电控调稳之后基本不用大改。
* **战术决策层（`decision.py`）**：
  只负责按比赛流程编排原子动作的调用顺序。比如先去 A 点抓球，还是先去 B 点防守。

```python
# decision.py: 清晰的线性业务流程
async def match_routine(fsm, act, bb):
    # 1. 移动并打点校正
    await act.navigate_to(bb.point_a)
    await act.correct_position_by_laser()

    # 2. 抓取作业
    await act.open_gripper()
    await act.grab_ring()

    # 3. 前往发射区
    await act.navigate_to(bb.point_shoot)
    await act.shoot()
```

这样设计的好处是：比赛前一晚如果要临时调整路线或行动顺序，你只需要在 `decision.py` 里改动函数的调用顺序，不用担心动到底层的硬件通信代码。

# 小结

1. **决策层用 Python 协程很合适**：逻辑编排不需要复杂的浮点运算，需要的是代码简洁直观和现场改路线的灵活性。
2. **拒绝同步阻塞**：`time.sleep` 会锁死当前线程，导致急停和传感器回调无法处理；利用 `await` 挂起让出控制权，保持事件循环通畅。
3. **电控无回包时的妥协**：机械无传感器或电控没写回调时，不得不做时间盲等。但务必使用异步的 `await asyncio.sleep` 或 `await fsm.wait`，并把时间抽离为配置参数，绝不用同步 `time.sleep`。
4. **注意回包竞态**：异步等待物理硬件响应时，遵循“先挂号，后发指令”，避免回包过快导致事件丢失。
5. **分层解耦**：底层硬件时序和盲等细节留在原子动作层，战术流程留在上层，改战术不影响通信。
